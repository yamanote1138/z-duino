Building Lights

Four tiny addressable LEDs, one per building, controlled individually from the Z-Duino web UI. They share a single data pin, run off the D1 Mini's USB 5V, and need no extra boards. Every building unplugs from the chain.

The layout

The controller sits in the main building, in the middle of the row. Pixels are daisy-chained, so the data goes out to the far end first (building 4) and then comes back toward building 1. Each hop between buildings is its own 3-wire cable (5V, data, GND) with a plug at each end. The main building keeps its status LED, which already lights its windows, so it gets no pixel.

How it's wired

Three wires leave the D1 Mini: 5V, GND and D8. A diode, a resistor and a capacitor sit inline near the board. From there, 5V, data and GND travel together through every plug and pixel.

Diode

An addressable pixel reads a "1" at 70% of its supply voltage. At 5V that is 3.5V, which a 3.3V pin only just misses. Dropping the pixel supply to about 4.3V lowers the threshold to about 3.0V, so the D1 Mini's output clears it with margin.

Resistor and capacitor

The 330Ω resistor protects the first pixel's input from spikes. The 220µF capacitor absorbs the surge when pixels switch on, which keeps WiFi and the motor PWM from seeing a dip on the USB rail.

Detachable buildings

Your JST-SYP 2.5 mm 3-pin pairs are wire-to-wire pigtails, which suits this exactly. The gender convention is what makes removal painless:

  • Each building's IN pigtail is male and its OUT pigtail is female. The D1 Mini's OUT pigtail is female too.
  • Each hop cable is male at the upstream end and female at the downstream end.
  • Pin order is the same on every connector: 1 = 5V (red), 2 = data (green), 3 = GND (black).

To remove a building mid-chain: unplug its IN and OUT pigtails. The hop cable that fed it now ends in a female socket, and the next one starts with a male plug, so the two plug straight into each other and the rest of the lights keep working. Removing B4 works the same way (hop 1 mates with hop 2). Removing B1, the last in the chain, needs nothing at all.

Building the cables

Pigtail leads are usually thicker (around 22 AWG) than the thin hop wire. Solder them together, heat-shrink each joint, and stagger the three joints so they cannot touch. Buzz out every finished cable with a multimeter before connecting any pixel.

At the pixel

The IN and OUT pigtails share the VDD and GND pads, so two wires land on each of those pads. Tin the pads first and check that your breakout has room.

Pin budget

Every digital pin on the D1 Mini is now accounted for. D8 was the only usable free output. A0 is free but input-only, and the track voltage readout is computed from the throttle (SUPPLY_VOLTAGE * currentSpeed), not measured.

Tools

Fine-tip soldering iron, flux, helping hands or a PCB holder, wire strippers, and a multimeter. Check for about 4.3V after the diode before connecting any pixel, and continuity-test every hop cable.

Already on hand

D1 Mini with USB power and the JST-SYP connectors. The firmware library (Adafruit NeoPixel) installs through PlatformIO, so there is nothing to buy for software.

Software plan

The change follows the existing structure: hardware-independent logic in lib/ with native tests, a thin hardware wrapper in the sketch, and a new panel in the web UI. Lights are independent of throttle and direction. The status LED code is untouched.

Protocol additions

// client to firmware (id = building 0-3, B1 = 0 ... B4 = 3; every field except id is optional)
{"cmd": "light", "id": 2, "on": true, "r": 255, "g": 150, "b": 50, "brightness": 0.6}
{"cmd": "lights_off"}

// firmware to client: status gains a lights array
{"type": "status", ..., "lights": [{"on": true, "r": 255, "g": 150, "b": 50, "brightness": 0.6}, ...]}

Brightness 0–1 from the UI maps onto a firmware cap (default 25% of the pixel's full output), so no slider position can overdrive a pixel or the USB supply. The default colour is a warm tungsten (255, 150, 50).

Risks and fixes

RiskFix
D8 (GPIO15) must be low at bootThe D1 Mini pulls it down already, and the pixel input idles low through the 330Ω resistor. No change needed.
Pixels flash random colours at power-upFirmware clears them first in setup(). The capacitor smooths the rail.
Pixel updates briefly disable interrupts (about 30µs per pixel) while the motor PWM is software-timedUpdate only on a change, never on a timer. If glitches ever show, move data to RX (GPIO3) with NeoPixelBus's DMA method.
USB current budgetAt the 25% cap, four pixels draw about 60mA at most, on top of the D1 Mini's WiFi peaks. A normal USB port covers it.
Mated connectors are a place for intermittent contactSeat each plug fully. If a pixel flickers or drops out, reseat the plugs upstream of it first. At about 60mA the contact resistance is not a power problem.
Wrong pin order on a hand-made cableSame order on every connector (5V, data, GND). Continuity-test each cable before it goes near a pixel.
Light bleeding through thin plastic wallsFoil tape or black paint inside each building, windows left clear.
Pixels wired in the wrong orderOne building-to-pixel constant in firmware. No rewiring needed.
Lighting 5V connected to the 12V track sideKeep the lighting on USB 5V only. The only link to the track side is the existing shared ground.

Open decisions

Decided: no pixel in the main building (the status LED stays), every building detachable with the JST-SYP pigtails.

  1. Remember light state across reboots. A debounced write to LittleFS would restore the lights after a power cycle. Recommended, but it adds a small amount of flash wear and a settings file.
  2. Default brightness cap. 25% is a starting guess. Real window brightness on your layout will tell us.
  3. Effects. Flicker, TV glow or a day/night fade are easy once the pixels work. Left for a later pass.
